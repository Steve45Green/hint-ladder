Insertion & In-order Traversal

By the end you can: insert a key into a BST by hand, write out its in-order traversal, and explain why that traversal always comes out sorted.

This deck is revision material, not graded. It covers two operations on binary search trees (BSTs): inserting a new key, and visiting every key in sorted order with an in-order traversal. Both operations lean on the same idea — the BST property — so understanding that property first makes the rest fall into place.

The BST property

For every node k, every key in its left subtree is smaller than k, and every key in its right subtree is larger.

This holds at every node, not just the root — each subtree is itself a valid BST.

Source: Cormen, Leiserson, Rivest & Stein, Introduction to Algorithms, 3rd ed., §12.1, p.286

A binary search tree is a binary tree where, at every single node, the BST property holds: everything in the left subtree is strictly smaller than the node's key, and everything in the right subtree is strictly larger. Because the property is recursive — it applies inside every subtree too — you can reason about the whole tree by reasoning about one node at a time. This one rule is what makes both insertion and in-order traversal work.

Insertion: walk down to find the spot

1. Start at the root. Compare the new key to it.

2. Go left if smaller, right if larger — repeat at each node.

3. When you fall off the tree (reach an empty spot), that is exactly where the new node belongs.

Source: Cormen, Leiserson, Rivest & Stein, Introduction to Algorithms, 3rd ed., §12.3, p.294

Insertion is just a search that fails on purpose. You walk from the root exactly as if you were looking for the key, comparing at each node and going left or right, and you remember the last node you visited. The moment the pointer you're following goes off the edge of the tree — hits an empty child — you stop: that empty spot is where the new node is attached, as a child of the last node you were at. Here, searching for 45 from the root (50): 45 < 50 so go left to 30; 45 > 30 so go right to 40; 45 > 40 and 40 has no right child, so 45 is attached there as 40's right child. Nothing else in the tree moves.

Insertion: pseudocode

x ← root;  parent ← NILwhile x ≠ NIL:    parent ← x    if key < x.key:  x ← x.left    else:            x ← x.right// x fell off the tree; parent is where we attachif parent = NIL:          root ← new node   (tree was empty)elif key < parent.key:    parent.left  ← new nodeelse:                     parent.right ← new node

The highlighted line is the one comparison that steers the whole walk — it runs once per level, so the loop takes as many steps as the tree is tall.

This is the standard iterative TREE-INSERT: two pointers, x tracking where the search currently is and parent remembering the last real node visited, since x becomes NIL at the exact moment we need to know its would-be parent. The loop body is just one comparison repeated: go left if the new key is smaller, right otherwise. Once the loop ends, three cases decide where the new node attaches — empty tree, attach as left child, or attach as right child — based on comparing the key against parent instead of x, since x is now NIL.

Worked example: building a tree

Insert, one at a time, into an empty tree:

50, 30, 70, 20, 40, 60, 80, 45

Walking through it: 50 is inserted first and becomes the root (the tree was empty). 30 < 50 goes left of 50. 70 > 50 goes right of 50. 20 < 50, < 30, so it lands left of 30. 40 < 50, > 30, so it lands right of 30. 60 > 50, < 70, lands left of 70. 80 > 50, > 70, lands right of 70. Finally 45 < 50, > 30, > 40, and 40 has no right child yet, so 45 lands as 40's right child — exactly the walk shown on the previous slide. Notice the insertion order shaped the tree: inserting the same eight keys in a different order can produce a different-looking tree, even though every one of those trees still obeys the BST property.
Check yourself

Starting from the tree above, where would inserting 65 attach?

65 > 50 → right to 70; 65 < 70 → left to 60; 65 > 60 and 60 has no right child → 65 becomes 60's right child.

Trace it exactly like the walk on the earlier slides: compare 65 to the root (50), go right since 65 > 50, land on 70; compare 65 to 70, go left since 65 < 70, land on 60; compare 65 to 60, go right since 65 > 60; 60 has no right child, so that empty spot is where 65 attaches.

In-order traversal: the rule

At every node, do three things in this order:

visit the left subtree, then the node itself, then the right subtree.

Apply the same rule recursively inside each subtree.

Source: Cormen, Leiserson, Rivest & Stein, Introduction to Algorithms, 3rd ed., §12.1, p.287

In-order traversal visits every node in a tree exactly once, in this order at each node: everything in the left subtree first, then the node's own key, then everything in the right subtree. Because it's applied recursively, "everything in the left subtree" itself means recursing with the same L-node-R rule, all the way down to the leaves. The name "in-order" is standard terminology contrasted with pre-order (node, left, right) and post-order (left, right, node) — the position of "node" in the sequence is what the name refers to.

In-order traversal: pseudocode

INORDER(x):    if x ≠ NIL:        INORDER(x.left)        visit(x)          // e.g. print x.key        INORDER(x.right)

Five lines, but it visits every node exactly once: the recursion bottoms out at NIL children, which is why leaves still get visited.

This is INORDER-TREE-WALK. The base case is x being NIL, which does nothing — that's what stops the recursion at the bottom of the tree. Otherwise, it recurses left first, then does the actual work on the current node (the highlighted line — printing or collecting the key), then recurses right. Because the left recursion always finishes completely before "visit(x)" runs, and "visit(x)" always finishes before the right recursion starts, the overall order across the whole tree is fully determined: left subtree's keys, then this key, then right subtree's keys.

Worked example: tracing the walk

Same tree as before. Numbers show visit order.

Output: 20, 30, 40, 45, 50, 60, 70, 80

Follow INORDER from the root, 50: first recurse fully into the left subtree (rooted at 30), which itself recurses left into 20 (visits 20, since 20 has no children — that's visit #1), returns up to 30 and visits it (#2), then recurses right into 40, which recurses right into 45 (visit #4, after first checking 45's empty left, so 45 alone is #4) — wait, carefully: at 40, recurse left (NIL, nothing happens), visit 40 (#3), recurse right into 45, which has no children, so visit 45 (#4). That finishes the left subtree of 50, so now visit 50 itself (#5). Then recurse into the right subtree rooted at 70: recurse left into 60 (#6), visit 70 (#7), recurse right into 80 (#8). Stitching the numbers together in order: 20, 30, 40, 45, 50, 60, 70, 80 — sorted.
Check yourself

If 65 had been inserted (as on the earlier check-yourself slide), where would it appear in the in-order output?

Between 60 and 70: …, 60, 65, 70, … — in-order output is always sorted, and 65 sits between those two values.

You don't need to re-trace the whole recursion to answer this: in-order traversal always produces sorted output, so a new key's position in that output is just its position in sorted order among the existing keys. 65 is greater than 60 and less than 70, so it slots in between them regardless of where it physically attached in the tree.

Why is the output always sorted?

At any node k: the left recursion visits only keys < k (BST property), then k itself, then only keys > k.

So around every single key, everything printed before it is smaller and everything printed after it is larger.

That is precisely what "sorted order" means — and it holds at every node, so it holds for the whole tree.

Source: Cormen, Leiserson, Rivest & Stein, Introduction to Algorithms, 3rd ed., §12.1, p.288 (Theorem 12.1)

This is the argument, and it's worth being able to reproduce it in an exam: the BST property guarantees that everything in a node's left subtree is smaller than the node, and everything in its right subtree is larger. In-order traversal visits left subtree, then node, then right subtree. Combine the two: for any node k, every key printed before k (from the left subtree) is smaller than k, and every key printed after k (from the right subtree) is larger than k. Since this is true simultaneously for every node in the tree, the whole output sequence has the property that it's non-decreasing from start to end — i.e. sorted. This is a proof by induction in disguise: it's really "if both subtrees print in sorted order, so does the whole tree," bottoming out at empty trees which trivially print nothing (sorted).

How much does this cost?

Insertion: one comparison per level walked down → O(h), where h is the tree's height.

In-order traversal: visits every node exactly once → O(n), for n nodes, regardless of shape.

h ranges from O(log n) for a bushy tree to O(n) for a skewed one (e.g. inserting already-sorted keys).

Source: Cormen, Leiserson, Rivest & Stein, Introduction to Algorithms, 3rd ed., §12.1, p.286

Insertion's cost is proportional to how far down the tree you walk before falling off, which is at most the tree's height h — so insertion is O(h), not O(n) or O(log n) outright, because h itself depends on the tree's shape. Traversal is different: INORDER visits every node exactly once no matter what, so it's always Θ(n) regardless of shape. The reason h matters so much: if you insert keys that are already sorted (1, 2, 3, 4, 5, …), every new key is larger than everything so far, so each one attaches as the right child of the previous one — the tree degenerates into a straight line, height n, and insertion becomes O(n) per key, O(n²) total. A roughly balanced tree instead keeps h around log₂(n), which is why balanced-BST variants (AVL, red-black trees) exist — they're a later topic, but the motivation is exactly this worst case.
Check yourself

You insert 10, 20, 30, 40, 50 in that order into an empty BST. What does the tree look like, and what is the insertion cost of the last key?

A straight line leaning right (10 → 20 → 30 → 40 → 50, each the right child of the last). Inserting 50 costs O(h) = O(4) comparisons — height grows with every insertion, so this is the worst case, O(n) overall for n keys.

Each new key is larger than every key already in the tree, so it always goes right, all the way down, then attaches as a new rightmost right child — a degenerate, linked-list-shaped tree. This is the worst case mentioned on the previous slide: height equals the number of nodes, so the k-th insertion costs O(k), and inserting n already-sorted keys costs O(1+2+…+n) = O(n²) total, versus O(n log n) for a well-balanced tree.

Summary

  • Insertion: walk down comparing against each node, left if smaller, right if larger, and attach at the first empty spot. Cost O(h).
  • In-order traversal: left subtree, then node, then right subtree, recursively. Cost O(n), and the output is always sorted — a direct consequence of the BST property.
