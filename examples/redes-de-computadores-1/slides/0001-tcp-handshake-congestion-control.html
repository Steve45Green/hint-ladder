TCP: The Three-Way Handshake and Congestion Control

By the end you can: read a Wireshark capture of a TCP connection, label the SYN / SYN-ACK / ACK handshake, and explain why the congestion window rises and falls.

This deck covers two linked topics from the transport layer: how a TCP connection is opened (the three-way handshake) and how TCP decides how much data it is safe to send once the connection is open (congestion control). Together they explain most of what you will see at the start and throughout the life of a TCP flow in a Wireshark trace. Press N to toggle these notes, → or space to advance.

Why a handshake at all?

  • Both sides must confirm they can send and receive before either trusts the connection.
  • Each side picks its own initial sequence number (ISN), usually pseudo-randomly, so old segments from a previous connection between the same two ports cannot be mistaken for new ones.
  • The opening segments also carry options — such as the maximum segment size — that both sides must agree on before data flows.

Source: Kurose & Ross, Computer Networking: A Top-Down Approach, §3.5.6

TCP is connection-oriented and reliable, so before either side sends real data they run a small protocol to agree on starting conditions. Three things get settled: mutual reachability (both directions work), the initial sequence number each side will count bytes from (chosen fresh per connection so segments cannot be confused with a earlier, closed connection reusing the same port pair), and connection options like the maximum segment size. This is why opening a TCP connection costs one extra round trip before any application data moves — you will see this cost directly in a Wireshark capture as three frames with no payload before the first data segment.

The three segments

Source: Kurose & Ross, Computer Networking: A Top-Down Approach, §3.5.6

Step through the three arrows. (1) The client sends a segment with the SYN flag set and its own initial sequence number, here 42; it carries no data. (2) The server replies with a segment that has both SYN and ACK set: SYN because the server also needs to announce its own initial sequence number (100), and ACK because it is acknowledging the client's SYN — the ack number is 43, i.e. the client's seq plus one, because the SYN itself counts as one byte for sequencing purposes even though it carries no payload. (3) The client acknowledges the server's SYN the same way: ack = 101 = 100 + 1, and its own seq is now 43, the next sequence number after its SYN. Once the client sends this third segment it moves to the ESTABLISHED state; the server moves to ESTABLISHED when this segment arrives. In Wireshark you can filter tcp.flags.syn==1 to see just these opening segments.

Worked example: the sequence numbers

After step 4, the client's first byte of data (if it sends any) will carry seq = 43 — the same number it used for the ACK, since the ACK itself carried no payload.

Source: Kurose & Ross, Computer Networking: A Top-Down Approach, §3.5.6

This is the same handshake as the previous slide, written as a trace so you can check the arithmetic yourself: an ack number is always "the peer's seq + 1" right after a SYN. Notice that seq=43 is reused: sending an ACK segment with no payload does not consume a sequence number, so the client's seq stays at 43 until it actually sends its first byte of data, which will then be numbered 43.
Check yourself

Using the numbers above (client ISN = 42, server ISN = 100): if the client's application writes data right after the handshake, what sequence number does the first byte carry?

43. The SYN consumed sequence number 42, so the client's next byte — the first real data byte — is numbered x+1 = 43. The final ACK of the handshake reused seq=43 without consuming it, since it carried no payload.

Answer from memory before revealing. The key idea to retain: SYN and FIN flags each consume one sequence number even with zero payload bytes, but a plain ACK with no data does not advance the sequence number. That is why the client's final handshake ACK and its first data segment can both legitimately carry seq=43 — the ACK doesn't "use up" 43, the first data byte does.

After the handshake: two windows limit the sender

The receiver advertises rwnd: how many bytes of buffer space it has free — this is flow control, protecting the receiver.

The sender separately tracks cwnd, the congestion window: how many bytes it believes the network can carry without overload — this is congestion control.

The sender may only have this many unacknowledged bytes in flight: min(cwnd, rwnd).

Source: Kurose & Ross, Computer Networking: A Top-Down Approach, §3.7

Once the connection is open, TCP still can't send unlimited data: two independent limits apply, and the sender must respect whichever is smaller. rwnd comes from the receiver's advertised window field in every segment — it protects a slow receiver from being overrun. cwnd is not advertised by anyone; the sender computes and adjusts it itself, based on signals of loss, as its estimate of how much data the network path between sender and receiver can hold without congesting a router queue. The rest of this deck is about how cwnd changes over time — that is what "TCP congestion control" means.

Slow start: probing for the ceiling

cwnd starts small — often 1 MSS — because the sender has no idea what the path can carry.

Every RTT in which all sent segments are acknowledged, cwnd doubles.

This continues until cwnd reaches ssthresh (the slow-start threshold) or a loss is detected — whichever comes first.

Source: Kurose & Ross, Computer Networking: A Top-Down Approach, §3.7.1

"Slow start" is a misleading name — cwnd actually grows exponentially, doubling every round trip. It is "slow" only compared to sending at full rate immediately. The reasoning: the sender has no measurement of the path's capacity, so it starts cautiously (1 MSS) but ramps up fast, because doubling each RTT still only takes a handful of round trips to reach a large window. Growth continues until cwnd hits ssthresh, an estimate carried over from a previous loss event (or a large default on a brand-new connection), at which point TCP switches to the much gentler congestion-avoidance phase described next.

Congestion avoidance: additive increase

  • Once cwnd ≥ ssthresh, growth switches from doubling to +1 MSS per RTT — linear, not exponential.
  • This is the "AI" half of TCP's AIMD (additive-increase, multiplicative-decrease) strategy: probe gently for more bandwidth once near the estimated ceiling.
  • Growth keeps going until a loss is detected — see the next two slides for what happens then.

Source: Kurose & Ross, Computer Networking: A Top-Down Approach, §3.7.1

Doubling cwnd forever would eventually overshoot the network's real capacity and cause a burst of loss. So once cwnd reaches ssthresh — the point where TCP believes it is close to the path's limit — it switches strategy: instead of doubling each RTT, it adds just one MSS per RTT. This is much more cautious, so even if the true ceiling is exceeded, the overshoot is small (one extra segment's worth) rather than a doubling's worth. The combination of fast exponential search followed by cautious linear probing, paired with the sharp cutback on loss you'll see next, is what gives TCP's congestion window its characteristic sawtooth shape over time.
Check yourself

Why does TCP grow cwnd exponentially at first instead of jumping straight to a large window?

The sender has no prior measurement of the path's capacity — unlike the ISN, which either side can simply choose, the network's capacity is unknown and can only be discovered by trying. Jumping straight to a large window risks flooding a slow link and losing many segments at once. Doubling each RTT (slow start) still reaches a useful window size in only a handful of round trips, while capping the damage if the real ceiling is much lower.

This connects the handshake and congestion-control halves of the deck: the ISN is something each host simply decides for itself, but the network's safe sending rate is not something either host can just decide — it has to be probed, because it depends on every router and link along the path, none of which TCP can see directly. That is the whole reason slow start exists.

Two ways TCP learns about loss

SignalWhat it meansNew ssthreshNew cwndNext phase
TimeoutNo ACK at all before the retransmission timer fires — assume severe congestioncwnd / 21 MSSSlow start
3 duplicate ACKsLater segments are still arriving (fast retransmit) — the path is not stalledcwnd / 2ssthresh (fast recovery)Congestion avoidance

Source: Kurose & Ross, Computer Networking: A Top-Down Approach, §3.7.1 (TCP Reno)

Both events halve ssthresh, since cwnd at the moment of loss is the best available estimate of "somewhat more than the network could actually carry" — halving it is the multiplicative-decrease half of AIMD. They differ in how far cwnd itself is cut. A timeout means nothing at all got through for a full RTO, a strong signal of serious congestion (or an outright lost segment with nothing behind it), so TCP Reno is conservative and restarts from cwnd=1 via slow start. Three duplicate ACKs mean later segments in the flow are still arriving and being acknowledged — only one segment seems to be missing — so Reno's fast-recovery mechanism sets cwnd directly to the new ssthresh and resumes the gentler congestion-avoidance growth, without dropping all the way back to 1. (The older, simpler TCP Tahoe treats both cases the same, always resetting to slow start; Reno's fast recovery is the version taught here and used in practice.)

Worked example: a cwnd trace with a timeout

RTT 1:  cwnd = 1            (slow start: 1 MSS)RTT 2:  cwnd = 2            (doubles)RTT 3:  cwnd = 4RTT 4:  cwnd = 8RTT 5:  cwnd = 16           (= ssthresh: switch to congestion avoidance)RTT 6:  cwnd = 17           (avoidance: +1 MSS per RTT)RTT 7:  cwnd = 18RTT 8:  cwnd = 19RTT 9:  cwnd = 20  -> TIMEOUT:  ssthresh = 20/2 = 10,  cwnd = 1RTT 10: cwnd = 2            (slow start resumes)

Source: Kurose & Ross, Computer Networking: A Top-Down Approach, §3.7.1

Walk the trace line by line. Slow start doubles cwnd from 1 to 16 over five round trips; at 16 it hits the (assumed) ssthresh of 16 and switches to congestion avoidance, adding 1 MSS per RTT for the next four rounds. At RTT 9, with cwnd at 20, a timeout occurs — nothing was acknowledged in time. TCP reacts by setting a new ssthresh to half of the cwnd it had reached (20/2=10) and cutting cwnd all the way back to 1, restarting slow start. Next time growth reaches cwnd=10 it will hit the new, lower ssthresh and switch to congestion avoidance sooner than the first time — the window "remembers" that the network could not sustain 20.

The sawtooth: cwnd over the life of a connection

Source: Kurose & Ross, Computer Networking: A Top-Down Approach, §3.7.1

This is the classic "TCP sawtooth" you will recognize in any plotted capture of a long TCP transfer. Read it left to right: an exponential climb (slow start) flattens into a straight-line climb (congestion avoidance) once ssthresh is reached, matching the two previous slides. At the marked timeout, cwnd is chopped all the way down to 1 MSS and the exponential climb restarts from scratch — a tall, narrow tooth. Later, at the marked triple-duplicate-ACK event, cwnd is only halved, and growth resumes immediately in the gentler linear mode — a shallower, less costly tooth. The shape of each drop is itself diagnostic: in a real capture, a deep drop back near the bottom followed by exponential-looking regrowth points to a timeout, while a shallow, roughly-halved drop followed by straight-line regrowth points to a fast retransmit.
Check yourself

On a plotted cwnd-vs-time graph you see two drops: one cuts cwnd almost to zero, followed by a curve that bends upward fast (concave); the other cuts cwnd to about half its previous value, followed by a straight line rising steadily. Which is the timeout and which is the triple-duplicate-ACK event?

The deep drop followed by fast, curving (exponential) regrowth is the timeout: TCP assumed severe congestion, reset cwnd to 1 MSS, and restarted slow start. The shallow drop to roughly half, followed by a straight (linear) climb, is the triple-duplicate-ACK event: fast recovery set cwnd directly to the new ssthresh and TCP resumed congestion avoidance without ever dropping back to 1.

This is exactly the reading skill the mission's Wireshark goal asks for: given a plotted or logged cwnd sequence, you should be able to tell which loss-detection path TCP took, purely from the shape of the drop and the shape of the regrowth that follows it, without needing to see the retransmission itself.

Summary

  • The three-way handshake (SYN, SYN-ACK, ACK) lets both sides confirm reachability and exchange initial sequence numbers before any data is sent; ack = peer's seq + 1.
  • After the handshake, the sender is capped by min(cwnd, rwnd): rwnd protects the receiver, cwnd protects the network.
  • cwnd grows exponentially (slow start) until ssthresh, then linearly (congestion avoidance) — AIMD's "additive increase."
  • Loss cuts cwnd sharply — to 1 MSS on a timeout, to half on a triple duplicate ACK — AIMD's "multiplicative decrease," producing the sawtooth.
